# 从提问到证据：批量归档与撤销的完整走查

[返回目录](../../README.md) · [提问的思想](../workflow/05-thinking-and-questioning.md) · [提问画布](../../templates/QUESTION-CANVAS.md)

> **独立虚构案例**：本章设计一个普通待办清单的“批量归档与撤销”功能，用于展示方法怎样改变开发决定。下文的需求、界面和操作记录均为教学构造；测试表是待执行的验收设计，未声称已有对应应用或实测结果。这里沿用[方法章的一手资料与使用边界](../workflow/05-thinking-and-questioning.md)。

## 1. 从一句功能要求找到真正的目标

初始要求是：“加个批量归档，最好还能撤销，界面清爽一点。”直接实施，容易把几项尚未确定的决定藏进代码：归档是否等于删除，清爽是否等于隐藏入口，撤销是否只在提示条出现时有效。

先用 JTBD 写一个工作假设：**当用户集中整理已完成事项时，希望一次移走选中的事项，同时能找回误归档内容，以便恢复一个便于查看的当前清单。** 真实项目应通过用户反馈或操作观察确认这一假设；本案例将它作为已选定的教学目标。

再用苏格拉底式提问收紧三个词：

| 模糊表述 | 会改变实现的问题 | 本案例选择 |
|---|---|---|
| 批量 | 处理全部事项，还是当前明确选中的事项？ | 只处理用户选中的事项，操作前显示数量 |
| 归档 | 记录被移出当前视图后，在哪里找回？ | 记录保留，可在归档页查看 |
| 撤销 | 提示条消失或应用重启后，是否仍能撤销？ | 示例要求：操作后十分钟内仍可从操作记录撤销 |

“十分钟”是本案例的产品选择，用来练习边界设计；实际时限应由需求确定。目标澄清后，第一条切片已经足够具体：**选中事项 → 归档 → 查看结果 → 在约定期限内撤销 → 验证恢复。**

可交给编码助手的指令：

```text
先勘察现有选择状态、归档接口和操作记录机制，标注真实文件位置。
以已选中的事项为范围，说明一次完整归档与撤销路径需要哪些行为。
沿用已有组件与数据约定。暂缓自动归档、跨设备同步和复杂筛选。
把“十分钟内支持重启后撤销”落实到可检查的状态与持久化要求。
```

## 2. 设计阶段：先保留必要条件，再比较界面

第一性原理在这里帮助拆开“清爽”与“少按钮”：完成任务至少需要知道选中了什么、将发生什么、执行到了哪一步，以及怎样恢复。控件是否常驻属于设计选择，关键的信息和恢复路径需要保留。

用双钻探索三种操作方式，再用权衡矩阵筛选：

| 候选方式 | 可能的优点 | 要观察的代价 | 当前证据 |
|---|---|---|---|
| 常驻工具栏 | 入口位置稳定 | 未选择时是否增加干扰 | 设计假设，待原型 |
| 选中后出现操作条 | 操作与选中对象联系紧密 | 出现时是否移动内容，键盘焦点是否清楚 | 设计假设，待原型 |
| 更多菜单中的归档 | 表面控件较少 | 首次使用是否难发现，操作步数是否增加 | 设计假设，待原型 |

本案例暂选“选中后出现操作条”，用于继续讨论。该选择尚未经过用户测试；应保留用原型观察推翻它的机会。让三种方式完成同一条任务，再比较找到入口、确认数量、执行与撤销的过程，比让模型给抽象的“高级感”评分更有用。

设计说明随之变成可以执行的要求：操作条显示选中数量；归档期间表达正在处理；完成后提供结果与撤销入口；失败时保留选中状态并给出下一步。操作记录页承担提示条消失后的恢复入口。键盘用户能到达这些控件，并在状态变化后知道当前位置。

```text
先做一个低成本原型，覆盖未选择、已选择、处理中、成功、失败五种状态。
检查窄屏下数量、动作名称和恢复入口能否同时理解。
用键盘完成选择、归档和进入操作记录；记录焦点变化。
根据实际观察决定是否继续使用这一交互方式。
```

## 3. 后端阶段：把撤销变成有边界的契约

系统思维要求沿操作追踪影响：选择集合进入请求，执行侧检查记录，持久化更新事项与操作回执，界面刷新当前列表和归档数量，撤销再读取同一份回执。只把“撤销按钮”加到提示条上，覆盖的仅是入口。

本例选择**整批成功或整批保持原状**的策略。某项记录已被编辑、状态不匹配或授权不足时，先返回可理解的冲突结果。需要部分成功的产品可以选择另一套契约，并相应设计结果展示。

| 场景 | 本案例约定 | 验证观察点 |
|---|---|---|
| 正常归档 | 更新本次选定记录，并保存足以解释和恢复该操作的回执 | 记录状态、操作回执、列表重新读取结果 |
| 某项记录版本已变化 | 整批保持操作前状态，指出需要重新确认的事项 | 更新前后快照、冲突结果 |
| 写入中途失败 | 事项更新与操作回执作为同一原子操作回滚 | 两类记录的一致性 |
| 响应丢失后重复请求 | 同一操作标识与相同请求内容对应同一结果 | 回执数量、事项版本、返回内容 |
| 相同操作标识却内容不同 | 返回请求冲突，保留原操作结果 | 请求摘要和回执对应关系 |
| 有效期内撤销 | 恢复本次操作改变的状态，保留原有记录身份 | 操作前后状态与记录标识 |
| 撤销前有后来编辑 | 本例采取保守策略：整批保持现状并报告冲突 | 版本比较、后来编辑的内容 |
| 重复撤销 | 返回已经撤销的结果，保持当前数据 | 回执状态、记录版本 |
| 超过十分钟 | 明确说明撤销期限已结束，仍可去归档页查看 | 服务端判定时间、界面说明 |

这些是行为规格，尚未指定编程语言与数据库实现。“原子操作”需要结合实际存储边界选择机制；涉及外部服务时，应重新设计补偿和恢复流程。多用户环境的授权由可信执行侧逐项核对，示例界面上的选择状态只是输入。

这里尤其要核对撤销的范围：恢复的是归档操作改变的状态，整行旧快照可能包含后来变动的标题或备注。可以先以版本检查拒绝冲突，再决定是否值得支持更细粒度的合并。

```text
对照这份契约寻找已有数据与事务边界。
为归档、请求重放和撤销各设计成功、冲突与中途失败的用例。
注明不变量在哪个边界成立，并解释回执与事项更新怎样保持一致。
实现前列出需要改变的接口；实现后用真实状态读取核对结果。
```

## 4. 调试阶段：一次点击，两次请求，先做哪项实验

假设联调时观察到一次点击对应两次请求。此时可以分别提出：

| 候选解释 | 可区分的预测 | 最小观察 |
|---|---|---|
| 按钮与表单重复触发 | 一次动作后出现两个独立的事件处理入口 | 事件入口记录与请求发起位置 |
| 网络失败后自动重试 | 第二次发送与重试条件相联系 | 响应、重试配置、发送时间与操作标识 |

把日志补到两个入口并记录一次完整操作，随后在隔离测试环境中只改变一项条件。若观察显示两个处理入口都被执行，可继续定位绑定关系；若只执行一次却重发请求，则追踪传输层。某个现象也可能由多项条件共同造成。

实验记录必须保存实际观察。“修完以后看起来好了”只能支持有限结论。最终至少需要区分：界面是否只发起预期动作，以及执行侧是否能正确处理重复请求。它们分别属于交互问题和数据正确性问题。

```text
先输出实验计划，再在授权的测试环境执行。
保留版本、复现输入、观察记录和改动的变量。
说明结果支持哪种解释、还有什么无法区分。
将定位到的条件写成回归测试，并重新检查请求重放契约。
```

## 5. 交付前：失败预演与恢复演练

假设发布后一位用户表示“我归档错了，而且找不回来”，可以列出三项值得检查的路径：

| 预演风险 | 需要核对的设计 | 待执行检查 |
|---|---|---|
| 提示条消失后无处撤销 | 操作记录页提供恢复入口 | 关闭提示条后进入记录页撤销 |
| 应用重启后回执消失 | 回执在约定期限内持久化保存 | 归档、重启、读取回执、撤销 |
| 撤销覆盖后来编辑 | 冲突检测与恢复范围明确 | 归档后编辑，再尝试撤销并核对内容 |

再按可逆决策拆开发布：新入口可以通过配置关闭，归档后的数据需要另外恢复。关闭入口应保留既有操作的查看和撤销路径，至少覆盖产品承诺的期限。数据库结构变更、历史回执保留与清理安排也需要单独确认。

这一步的产物应是一份可执行的恢复安排：停止什么、保留什么、怎样识别受影响记录、由谁执行，以及通过哪些数据确认恢复。演练优先使用测试副本；真实数据操作需要相应权限与备份安排。

## 6. 接手与复盘：留下能被下一次使用的知识

自我解释练习可以只问三个问题：我能解释回执为何需要持久化吗？我知道响应丢失后怎样查询结果吗？我能预测归档后又编辑记录时的撤销行为吗？答案应能指向真实代码和验证记录。

若之后真的发生过“重启后无法撤销”，再根据事实做事后复盘。检查需求是否明确期限与重启语义、验收是否只看同一会话、回执是否落盘、错误是否可见。将改进落实到最接近问题的位置，例如增加重启后撤销的集成用例，并在任务模板提醒持久化边界。
