# 把模糊感觉说成准确的修改指令

[返回目录](../../README.md) · [视觉词典](../frontend/01-visual-language.md) · [提示词配方](../workflow/02-prompt-recipes.md)

好的指令包含一个观察、一个目标、一个范围和一种确认方式。你可以保留“我想更优雅”的感觉，再补上可执行的细节。下面的改写是本手册建议，适合按项目情况调整。

## 一、前端：从观感走到可见的决定

| 原先想说 | 更准确的表述 | 验收重点 |
|---|---|---|
| 高级一点 | 用克制的色彩和清楚的字体层级建立质感；强调主要内容，统一边界、间距和图标笔画 | 一屏的强调对象明确，细节一致 |
| 优雅一点 | 调整标题、正文、辅助信息的比例，给内容之间稳定的节奏，让动效只解释状态变化 | 看阅读顺序与交互连贯性 |
| 太空了 | 在维持字号和可点击区域的前提下，提高列表信息密度，合并重复容器和标题 | 同尺寸可扫描更多有效内容 |
| 太挤了 | 区分相关项内部间距与组间间距，减少同屏次要动作，展开项保留完整信息 | 分组更清楚，任务仍完整 |
| 像AI模板 | 根据主要任务重排信息，使用定制内容结构；为每个大卡片说明它的独立职责 | 结构能解释产品特征 |
| 配色很乱 | 建立中性色表面、主强调色和状态色；颜色使用语义token统一管理 | 同类含义使用同类颜色 |
| 有点土 | 请指出造成观感的具体因素，先比较字号、字重、色彩数量、圆角和阴影，再选三项调整 | 有具体问题和前后比较 |
| 动画丝滑点 | 状态过渡应短促、可打断，优先动画化透明度或位移；支持减少动态效果的系统偏好 | 无明显跳变，快速连续操作稳定 |
| 现代一点 | 采用清楚的组件边界、稳定的排版尺度、细致状态和合理的响应式布局 | 观感与任务完成一起改善 |
| 按钮不明显 | 在当前区域设一个主动作，通过填充、位置与文案突出；次要操作降低视觉权重 | 首次进入能找到下一步 |
| 弹窗不好用 | 确认它是否需要阻断当前任务；若只查看详情，尝试侧栏；若要作决定，保留对话框并管理焦点 | 返回路径、键盘与原任务连续 |
| 图标不统一 | 使用同一图标集、光学尺寸与笔画风格，图标按钮补可访问名称 | 不同图标视觉重量接近 |
| 感觉不对齐 | 检查容器边界、文字基线、图标光学中心与表单标签的对应关系 | 逐列/逐行比对，无意外偏移 |
| 长内容很难读 | 区分阅读和扫描模式，正文限制行长并保持舒适行距，表格提供稳定列头 | 中文、英文和代码各自可读 |

“现代、优雅、专业”是方向词，真正驱动实现的是后半句。若你无法定位问题，可以请模型先做三条诊断，每条附截图区域与影响，再选择优先级。

## 二、后端：把品质词转成运行行为

| 原先想说 | 更准确的表述 | 验收重点 |
|---|---|---|
| 稳一点 | 列出这次操作最可能失败的两处，确认失败后数据与任务状态仍可解释，并验证恢复路径 | 真实失败后的状态与恢复 |
| 快一点 | 先测用户可感知的等待发生在哪一段，再优化最大瓶颈；用相同样本复测 | 测量方法、前后数据与环境 |
| 优化数据库 | 先找慢查询或重复读写，检查查询计划、索引和事务长度，再提出最小改动 | 查询证据与正确性 |
| 处理一下并发 | 说明两个请求同时到来时共享什么状态，找会覆盖或重复执行的地方 | 可复现的并发场景 |
| 加重试 | 区分可恢复与永久错误，给出次数、等待、总截止时间和幂等前提 | 重试不会造成重复副作用 |
| 支持取消 | 定义取消请求如何传播，哪些已提交结果会保留，以及谁确认最终状态 | 后台结果与UI一致 |
| 报错友好点 | 返回稳定的错误类别，界面用可理解的文字解释结果与下一步，保留可定位的诊断标识 | 用户能行动，开发者能定位 |
| 写得规范点 | 对照当前项目约定，先指出影响正确性或维护的具体问题，再做最小改动 | 明确收益与有限diff |
| 拆一下代码 | 找职责交织或变化频率不同的部分，保持外部行为，拆出能独立理解的边界 | 接口清楚，行为保持 |
| 彻底review | 明确本次改动范围和高风险用户路径，按严重度列有证据的发现，说明未覆盖部分 | 范围、证据、影响、缺项 |
| 做好日志 | 记录任务标识、阶段、结果、耗时和错误类别；按数据敏感性控制内容 | 一次失败能沿同一标识追踪 |
| 接上大模型 | 先核对已有运行时和适配层，从配置→调用→流式/结果→保存打通一个用户路径 | 真实配置有实际消费者 |

有关术语的技术含义与官方依据见[后端地图](../backend/01-backend-map.md)及[数据、异步与边界](../backend/03-data-async-security.md)。这张表主要帮助你组织任务。

## 三、从截图提出一次高质量评审

你可以写成下面这样：

```text
这是当前资料列表的截图，目标用户需要连续筛选和阅读产品文档。
目前我看到三个问题：
1. 主要按钮、状态标签和标题同样突出，注意力分散。
2. 每行有多层容器，资料标题占到的宽度偏少。
3. 选中行与键盘焦点看起来一样，容易混淆。

请先确认这些观察是否成立，再按任务影响排序。
在既有设计系统内调整视觉层级、行结构和状态表达。
保持字段、功能与数据行为，交付相同视口、相同数据的前后截图，
并验证鼠标与键盘都能打开所选资料。
```

这段允许模型纠正你的观察，也把范围和证据说清。审美判断可以协商，数据行为和操作路径则有明确的事实依据。

## 四、提出问题时，把猜测和事实分开

“我点了取消，十秒后结果还在出现”是观察；“肯定是 WebSocket 有问题”是猜测。可以一起告诉模型，但先让它定位链路。

```text
观察：[发生了什么；复现步骤；时间/环境；预期]。
我的猜测：[可能的原因，供参考]。
请先用代码和运行证据判断原因，给出最小修复与相关验证。
如存在多个解释，先列能区分它们的检查，再执行信息量最高的一项。
```

这种表达能保留你的直觉，同时给诊断留下基于证据修正的空间。

## 五、什么时候一句话足够

已有上下文、影响很小、验收直接的任务可以很短：

> 将详情面板的“打开”按钮文案改为“打开原文”，同步现有英文文案，沿用组件样式。

跨接口、数据与平台的任务需要更多上下文。你在任务说明中投入的篇幅，与它影响的范围保持相称即可。
