> **使用方式**：挑一份最接近当前任务的模板，替换 `{{占位符}}`，删除用不到的栏目。它们是自然语言任务模板，粘贴到 Claude Code、Codex、Cursor 或其他具备相应能力的代理会话即可；是否能读文件、运行程序、操作浏览器，取决于所在环境。

## 先掌握三种语气

| 模式 | 开头怎么说 | 你会得到什么 |
|---|---|---|
| 只读检查 | “请只读检查，输出依据与建议。” | 现状、问题、方案；代码维持现状 |
| 给定范围内执行 | “请完成下面这项改动，并验证。” | 实际改动和验证结果 |
| 先解决未知项，再继续 | “先核实这些事实；在既定目标和权限内，按证据选择方案并完成。” | 必要调查与连续实施 |

要模型真的做事，就明确写“完成”“修改”“验证”；需要审查时，写清“只读”和比较基线。对完成标准使用操作和结果，例如“重启后能打开原记录”，比“代码很健壮”更容易验收。

<a id="p01"></a>
## P01 · 只读认识当前仓库

**适用**：新会话、新模型、久未打开的项目。**输入**：任务目标和仓库路径。**验收**：能指出真实入口与相关验证方式。

```text
请先只读认识当前仓库，为这项任务建立准确背景：{{任务目标}}。

1. 确认仓库、当前分支、最近提交、未提交改动与生效的项目说明。
2. 按当前代码追踪相关用户入口、业务逻辑、数据存储和测试入口。
3. 找到已经存在、可以复用的机制；区分当前实现与历史设计。
4. 核实项目实际使用的包管理器和验证命令。

请输出：事实表（结论、文件位置、依据）、最小相关文件清单、
尚需确认的未知项，以及下一步最小可执行任务。
这一轮只读；只运行明确的只读检查。遇到运行脚本时先阅读脚本内容。
不确定的判断标为假设，并给出验证它的具体办法。
```

**看结果**：文件清单应围绕任务，能够解释每个文件为什么相关。完整目录树通常不如一条真实调用链有用。

<a id="p02"></a>
## P02 · 把一个想法收敛成一页 brief

**适用**：“我想要这种感觉/这种功能”，但还没有清晰边界。**验收**：普通使用者能按验收步骤判断效果。

```text
我的想法是：{{自然语言描述}}。
使用者与主要情境：{{谁、何时、做什么}}。
当前项目背景：{{相关文档或已有页面}}。

请结合现有实现，把它整理成一页任务 brief：
目标、现在的问题、核心用户流程、本次范围、复用机制、
验收场景、暂留后续的内容。

先从现有材料补齐信息；常规实现选择由你做合理判断。
只有会明显改变产品方向或数据处理方式的未知项，才列为待决策。
验收写成“给定某种状态，做某项操作，应看见某个结果”。
最后给出一个最小首版和一个后续增强项，并说明先做首版能学到什么。
这一轮输出 brief，供我选择方向。
```

<a id="p03"></a>
## P03 · 完成一个已确定的小任务

**适用**：任务明确，期待代理连续推进。**验收**：小范围差异、行为正确、证据充分。

```text
请完成这项改动：{{目标}}。
相关入口：{{文件、页面或功能}}。
约束：{{当前项目约定、需要复用的机制}}。
验收：{{2—4个可以观察的场景}}。

先确认现有实现和工作区状态，然后在本任务范围内直接完成。
用项目现有方式实现；新增依赖或跨模块调整应有具体必要性。
保留其他人的现有改动。验证本次行为，并运行项目规定的交付 gate。

结束时说明：改变了什么、为何这样做、实际执行的检查和结果、
仍需在哪个环境确认，以及当前分支/提交状态。
如果一个必要步骤受到真实限制，先完成其余能完成的部分，再准确说明阻碍。
```

<a id="p04"></a>
## P04 · 把大功能切成完整的小交付

**适用**：看起来需要改很多模块的功能。**验收**：第一片完成后就能实际使用。

```text
目标功能：{{大功能}}。
目前已有：{{现有能力}}。
最重要的用户任务：{{核心任务}}。

请结合当前代码，把工作拆成少量垂直切片。
每片都写清：用户能做什么、涉及哪些层、输入与输出、
依赖前一片的什么，以及如何独立验收。

优先让第一片走通界面入口、真实业务和持久化结果。
把视觉补充、更多格式和非关键扩展放到后续合适的位置。
沿用项目当前 brief 与任务管理方式，避免重复创建一套流程。
在目标与约束已明确的情况下，完成第一片并提交验证证据。
```

<a id="p05"></a>
## P05 · 先定艺术方向，再落地一版

**适用**：页面结构已知，但视觉气质模糊。**验收**：方向有具体差别且能指导实现。

```text
请为 {{产品/页面}} 建立视觉方向。
用户与任务：{{使用者、信息密度、使用时长}}。
参考：{{截图或链接}}，我喜欢其中的 {{具体特征}}。
需要延续的视觉资产：{{字体、品牌色、组件或现有规范}}。

先提出两种清楚可比较的方向，用以下维度说明差异：
版式结构、字体层级、背景与表面层次、强调色、间距与密度、
边框与阴影、图标、动效、适用场景。
每种方向用一段具体描述和一组关键参数表达，避免只有形容词。

若项目已有批准的视觉规范，围绕它做精炼；风格探索以我的任务范围为限。
根据 {{我指定的方向/与当前产品最一致的方向}} 完成一版可检查的实现。
给出设计决定及对应截图，说明这些决定怎样支持主要任务。
```

**补充词汇**：“清晰的视觉层级”“低干扰的表面层次”“编辑式排版”“紧凑但有分组节奏”“单一强调色”。每个词后接一个实际对象，例如“侧栏采用低对比表面，当前项目用边线和文字共同标识”。

<a id="p06"></a>
## P06 · 根据截图做高质量设计反馈

**适用**：界面“总差一点”，但说不准哪里。**验收**：每条反馈可定位、可修改、可比较。

```text
请审阅这张实际界面截图：{{截图}}。
页面目的：{{主要任务}}；窗口尺寸：{{尺寸}}。
视觉目标：{{期望气质或设计规范}}。

按信息层级、布局比例、排版、色彩与对比、间距、组件一致性、
状态表达和操作可发现性检查。
先指出最影响体验的3—5个问题。
每条用“具体区域 → 可观察问题 → 用户影响 → 修改方案 → 验收方式”表达。

把纯审美偏好和任务可用性问题分开。截图看不到的交互标为待检查。
这一轮先给设计诊断；若我已经授权你修改，则按优先级完成修正并给对比截图。
```

<a id="p07"></a>
## P07 · 从现有界面提炼设计系统

**适用**：组件越写越多、颜色间距开始散乱。**验收**：减少重复规则，同时保持既定气质。

```text
请从 {{现有页面/组件目录/设计文件}} 提炼一个够用的设计系统。
先盘点已经在用的字体、颜色、间距、圆角、边框、阴影和组件变体。

把重复值整理为有语义的 tokens：表面、主要文字、次级文字、
边框、强调、成功、警告、错误、焦点，以及空间和字号层级。
说明哪些值值得统一，哪些差异由使用情境合理决定。

在 {{限定组件范围}} 中应用这些约定，沿用现有样式工具。
核对默认、悬停、键盘焦点、禁用、加载、选中和错误状态中实际适用的项目。
交付 token 对照、组件规则和实际截图，并说明后续新组件怎样复用。
```

<a id="p08"></a>
## P08 · 补齐交互状态与键盘路径

**适用**：正常状态好看，等待或失败时混乱。**验收**：用户始终知道发生了什么、下一步做什么。

```text
请完善 {{功能}} 的状态与交互。
主要流程：{{操作顺序}}。

先列出此功能实际需要的状态：初始、空数据、加载、部分完成、
成功、失败、取消、离线或重连；删去与场景无关的项。
对每个状态说明：界面内容、可用动作、焦点位置、数据是否保存、
如何回到稳定状态。

复用现有状态管理与组件。检查键盘操作、可见焦点、明确标签、
错误提示与操作控件的关联。持续任务给出真实阶段或活动反馈。
完成实现后，走一遍成功路径和最重要的两条异常路径，记录实际结果。
```

<a id="p09"></a>
## P09 · 把“它坏了”变成稳定复现

**适用**：偶发错误、描述模糊、模型已经猜了几轮。**验收**：给另一位开发者同样输入也能看见问题。

```text
我观察到：{{现象}}。
期望行为：{{期望}}。
发生环境与操作：{{系统、版本、步骤}}。
现有证据：{{脱敏日志、截图、错误信息}}。

请先定位并复现，暂缓修复。
确认真实入口，记录最短操作序列、必要初始状态、实际结果与期望差异。
如果无法复现，区分“环境缺失”和“条件尚未找到”，并给出下一项最小实验。
提出最多3个有代码依据的假设，说明每个假设怎样验证或排除。
保留复现 fixture 或可重复操作步骤，供后续修复前后对照。
```

<a id="p10"></a>
## P10 · 依据复现做最小修复

**适用**：已经知道触发路径。**验收**：原问题消失，相关行为保持正确。

```text
请修复以下已复现的问题：{{问题}}。
复现步骤与证据：{{内容}}。
相关约束：{{已有契约、数据兼容性等}}。

沿真实调用链找出第一次偏离预期的位置，解释根因。
选择能修正原因的最小改动，保持本任务之外的架构与接口稳定。
为这类问题增加有价值的回归检查：能够在修复前失败，修复后通过。
如果无需自动化测试，用可重复人工步骤说明原因和覆盖范围。

执行原复现路径及最接近的边界路径。
报告根因、修改依据、验证结果和任何仍需特定环境确认的部分。
```

<a id="p11"></a>
## P11 · 对一条后端路径做只读 review

**适用**：检查数据、权限、错误处理，时间有限。**验收**：有依据的问题、明确的覆盖边界。

```text
请只读审查 {{接口/IPC命令/业务操作}}，预算约 {{15/30}} 分钟。
比较基线：{{分支、commit或未提交差异}}。
预期行为：{{要求}}。

从输入开始，依次追踪身份与权限、参数验证、业务约束、
数据写入、外部调用、返回结果与日志。
优先检查重复提交、并发修改、超时、取消、部分失败和重启恢复。
根据实际部署环境区分本地桌面与公网服务的风险。

每个发现给出位置、触发条件、用户影响、证据和最小修正方向。
将已确认问题、待验证假设和非阻塞建议分开。
最后列明实际审查范围、执行过的检查和残余风险；这一轮保持只读。
```

<a id="p12"></a>
## P12 · 审查数据结构或迁移方案

**适用**：表结构、文件格式、索引或持久化语义变化。**验收**：现有数据有清楚的兼容和恢复路径。

```text
计划中的数据变更：{{变更}}。
现有数据与版本：{{当前schema、样例或迁移文件}}。
项目已有迁移约定：{{位置}}。

请先只读核对：旧数据如何读取、何时迁移、迁移失败如何表现、
再次启动是否可恢复、备份是否覆盖实际需要的数据。
明确区分主数据、可重建索引和缓存。

给出最小迁移方案、前置条件、失败恢复办法和验证场景。
如已获得本任务的实施授权，先在临时副本或fixture上实现与验证；
涉及实际用户数据库的迁移，应以已确认的目标和授权范围执行。
交付迁移前后样例、数据保留检查与尚需处理的兼容问题。
```

<a id="p13"></a>
## P13 · 检查流式输出、取消和重试

**适用**：AI 任务、后台解析、模型调用、网络连接。**验收**：操作状态与实际工作一致。

```text
请检查 {{长任务/流式功能}} 的状态与恢复语义。
当前实现入口：{{路径}}；预期操作：开始、取消、重试、恢复。

追踪任务ID、一次尝试的ID、事件顺序、持久化时间和最终状态。
核对：取消是否传递到实际工作；重试是否重复创建数据或产生额外副作用；
断线后恢复的是已有任务还是开启新任务；迟到事件是否覆盖终态。
若涉及模型调用，记录实际模型绑定、工具调用结果和可追溯的来源标识。

先画出实际状态转换，再针对有证据的问题做范围内修复。
验证正常完成、执行中取消、断线重连和失败后重试。
报告观察到的行为，并明确模拟测试与真实外部服务测试的区别。
```

<a id="p14"></a>
## P14 · 给第二个模型做独立 review

**适用**：重要行为完成后，需要与实施者视角分离。**验收**：审查结果可复现且忠于需求。

```text
你担任这项变更的独立审查者，先保持只读。
原始要求：{{brief}}。
比较范围：{{base与head，或具体diff}}。
关键项目约定：{{文档}}。
现有验证证据：{{结果}}。

先根据要求与代码独立判断，再参考实施者解释。
优先找真实行为缺陷、遗漏的边界和证据不足的完成声明。
沿相关调用链核实推断；必要时运行明确的针对性检查。

每个finding包括：优先级、位置、触发条件、影响、依据和修正方向。
把需要补充证据的疑问单列；纯风格建议单列。
如果没有确认缺陷，说明审查范围与仍未覆盖的情境。
```

<a id="p15"></a>
## P15 · 有判断地处理审查意见

**适用**：模型审查意见很多，真假和轻重混在一起。**验收**：每条重要意见有处理依据。

```text
请处理这份review：{{意见}}。
结合原始任务和当前代码逐条核实。

对每条意见给出：成立、部分成立、需要更多证据，或已有代码已处理。
用代码路径、复现或验证结果支持判断。
优先修复成立且影响正确性的项目；设计建议按当前任务范围取舍。
修复后重新执行对应复现与必要回归检查。

输出简短处理表：意见、判断、改动、验证、剩余事项。
若某条建议会改变既定产品语义，先提出具体选择及影响。
```

<a id="p16"></a>
## P16 · 做一个保持行为的局部重构

**适用**：重复逻辑、难读函数、模块边界模糊。**验收**：维护成本降低，原行为有对照。

```text
请重构 {{限定区域}}，目的是 {{具体维护问题}}。
已有外部行为与约束：{{接口、状态、数据格式}}。

先说明当前复杂度来自哪里，以及最小重构能减少哪项负担。
复用已有抽象，优先调整命名、职责和局部重复。
保留对外行为；把确有必要的行为变化作为单独事项说明。
用现有测试或少量针对性检查建立重构前后的行为对照。

完成后解释：职责如何更清楚、哪些重复被合并、调用方受到什么影响，
以及如何证明原功能保持正确。
```

<a id="p17"></a>
## P17 · 先测量，再优化性能

**适用**：“感觉慢”“列表卡”“打开要等很久”。**验收**：有可比测量和实际瓶颈依据。

```text
性能问题：{{具体慢在哪里}}。
典型数据规模和环境：{{数量、设备、系统、运行方式}}。
目标：{{响应时间或体验要求，未知可标待测}}。

请先建立可重复的测量，拆分界面渲染、业务处理、磁盘/数据库和外部请求耗时。
给出基线、测试条件和主要瓶颈，区分冷启动与重复操作。
选择一项收益明确、改动可控的优化，保持现有功能语义。
在相同条件下复测，记录样本与波动。

交付优化前后结果、原因解释和剩余瓶颈。
若当前环境无法测量目标设备，明确可支持的结论及实机需要补测的步骤。
```

<a id="p18"></a>
## P18 · 判断是否需要新增或升级依赖

**适用**：模型提议“装一个包就好了”。**验收**：新增成本与收益有明确理由。

```text
需求：{{能力}}。
候选依赖或升级：{{包名/版本}}。

先查当前仓库是否已有能完成任务的机制。
核验候选依赖的官方文档、版本兼容性、运行环境、许可证和必要配置。
比较继续复用、少量自实现、引入该依赖三种方案的实际成本。
给出与你观察到的代码相符的建议，避免只依据下载量或流行度。

若本任务已授权新增/升级且理由充分，使用现有包管理器完成，保持锁文件一致。
检查安装脚本与配置影响，运行相关验证，并给出回退到原依赖状态的办法。
```

<a id="p19"></a>
## P19 · 检查测试是否真的证明了目标

**适用**：测试全绿，但仍担心接线错误或测试自我重复。**验收**：知道每条检查能证明什么。

```text
这项改动的目标：{{行为}}。
现有测试与验证结果：{{路径和结果}}。

请审查验证设计：每个关键验收由哪个检查覆盖，
哪些依赖被mock，哪些真实模块参与，哪些边界仍靠人工。
关注测试是否只重复实现细节、是否绕开实际接线、
以及能否发现这项功能最可能出现的回归。

针对具体缺口补最少且有价值的验证。
对纯文案或低影响样式改动，可采用截图和操作验证。
输出“验收点—证据—剩余范围”对应表，并区分已执行与建议执行。
```

<a id="p20"></a>
## P20 · 组织多模型或多代理并行

**适用**：调查、前后端、设计与审查可独立推进。**验收**：各自工作能顺利整合。

```text
总目标：{{目标}}。
可用执行环境：{{工具、模型、工作目录}}。
当前项目协作约定：{{约定}}。

先识别可并行的独立工作，再给每个任务明确文件归属、输入、输出和验收。
共享类型、契约、迁移和同一文件由一位负责人协调。
必要时使用独立分支/worktree；同时安排独立端口、临时数据与运行目录。

各实施者交付具体差异和证据，整合者负责接口一致性与最后的用户路径验证。
把独立审查放在实施之后，保留对原始要求的访问。
在已确定目标内直接推进，并及时汇报发现的依赖冲突及解决方式。
```

<a id="p21"></a>
## P21 · 为新会话写精简交接

**适用**：上下文将满、更换模型、隔几天再继续。**验收**：接手者能核对现场后立即做下一件事。

```text
请为当前工作写一份精简handoff，沿用项目已有交接位置和格式。
包含：
1. 当前目标和本次已确认的约束。
2. 真实仓库、分支、commit及未提交状态。
3. 已完成行为、关键文件、实际验证结果。
4. 已证伪的假设、尚未解决的问题与证据。
5. 下一项最小任务、验收办法和所需环境。

保留决定与事实，压缩聊天过程。
明确标注历史方案、当前事实、建议和待验证项。
私有材料留在原项目受控位置，公开交接仅保留必要的脱敏说明。
最后写一段接手提示：先复核当前工作区，再继续哪一步。
```

<a id="p22"></a>
## P22 · 完成提交前交付说明

**适用**：功能已完成，需要留下可读的版本记录。**验收**：说明与实际差异一致。

```text
请完成 {{本次任务}} 的交付整理。
先检查最终diff，确认只包含本任务相关改动，保留其他人的现有工作。
核对任务验收与项目规定的交付gate，整理实际结果。

更新受到行为变化影响的现有文档。
按仓库和本次任务已授权的方式准备commit或PR；若只要求本地成果，
就保留本地状态并给出可直接使用的提交说明。

交付文字请包括：原问题、具体改变、现在的使用行为、验证证据、
必要的兼容或部署事项，以及未完成的范围。
让下一位读者无需翻阅整段聊天就能理解这次改动。
```

## 为任意模板添加一个“证据尾巴”

当模型常常说得漂亮、实际证据不足时，在任务末尾加这段：

```text
请把最终结论区分为：
- 已执行并观察到：附命令/操作、结果和对应文件或截图。
- 由代码阅读支持：附实现位置与推断条件。
- 尚待验证：说明缺少哪个环境或输入，以及最小补验步骤。
完成声明应当与这三类证据一致。
```

需要减少来回确认时，加这段：

```text
在已确定目标、项目约定和现有授权内，常规可恢复的实现选择由你决定并继续。
只有真实阻碍或会明显改变产品方向、数据安全、外部发布范围的决定，
才提出具体选项和影响。先完成所有与该决定无关的工作。
```
