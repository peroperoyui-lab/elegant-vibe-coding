# 提问的思想：让问题推动开发

[返回目录](../../README.md) · [AI 编码工作流](01-agentic-workflow.md) · [提示词配方](02-prompt-recipes.md) · [完整案例](../cases/04-question-to-evidence.md)

> **本章定位**：面向与编码助手协作的人，介绍如何选择问题、形成判断并进入实现。这里的 12 种方法是本手册按开发任务组织的选编，各自的理论范围与证据基础有所不同；开发指令、组合方式和停止条件为本手册的实践建议。示例均为独立构造的教学情境。
>
> **资料核验：2026-10-22。** 来源列于文末，并在相应方法旁标注。人的学习研究、企业经验和工程方法分别说明，迁移到 AI 协作的效果仍需在实际任务中检验。

## 1. 好问题应当改变下一步动作

“怎样让应用更好？”可以启动讨论，却很难直接决定改什么。“用户是在寻找入口时停住，还是在保存失败后失去进度？”则能把下一步分成两条：前者观察任务路径，后者检查状态与恢复。

提问的价值，在于把一个模糊愿望转成可判断的差异。每个重要问题都应连接到某个决定：回答 A 时做什么，回答 B 时做什么，以及需要什么证据才能选择。若两个回答最终都导向同一项低风险修改，这个问题可以暂存，先推进已经确定的部分。

一个实用的推进顺序是：**观察具体情境 → 找到关键未知 → 选择一种方法 → 留下一项产物 → 执行或验证。** 产物可以是任务目标、界面草图、接口约定、实验记录或回归测试。问题变多、措辞变专业，本身都不足以说明进展。

### 先区分四种信息

| 类型 | 意思 | 开发中的写法 |
|---|---|---|
| 事实 | 已在当前材料中观察到的内容 | “这个版本点击一次归档，网络面板记录了两次请求。”附版本与记录 |
| 假设 | 对事实的待检验解释 | “可能同时绑定了按钮事件和表单提交事件。” |
| 偏好 | 需要人做出的价值选择 | “这个工具优先保留紧凑布局。” |
| 约束 | 当前必须满足的条件 | “本次保留原数据格式，且需要支持键盘操作。” |

模型可以协助寻找事实、提出假设与比较方案。偏好由目标使用者或负责人决定；约束应注明来源和有效范围。把“常见做法”写成可讨论的选择，把“已经观察到”与“预计如此”分别记录。

## 2. 按当前卡点选择方法

下面的对应关系是阅读入口，同一种方法也可以跨阶段使用。日常任务通常先选一种，必要时再加一种互补方法。

| 现在卡在哪里 | 首选方法 | 它追问什么 | 留下什么 |
|---|---|---|---|
| 大家使用同一个词，却理解不同 | [01 苏格拉底式提问](#m01) | 这个判断具体指什么？ | 定义、例子与反例 |
| 功能很多，却说不清价值 | [02 待完成任务 JTBD](#m02) | 用户在什么情境下想取得什么进展？ | 情境化目标 |
| 方案受惯例或技术名词支配 | [03 第一性原理](#m03) | 哪些条件必须成立，哪些只是现有做法？ | 最小要求与待验证前提 |
| 太早锁定唯一方案 | [04 双钻](#m04) | 问题和解法各有哪些可能？ | 问题定义与候选原型 |
| 几个方案都合理 | [05 权衡矩阵](#m05) | 按哪些条件选择，证据有多强？ | 可解释的选择记录 |
| 局部修改牵动多个环节 | [06 系统思维](#m06) | 影响沿什么路径传播和反馈？ | 影响关系与观察点 |
| “正确”“成功”缺少共同标准 | [07 契约与不变量](#m07) | 操作前后保证什么？ | 行为约定与测试条件 |
| 一直猜故障原因或性能瓶颈 | [08 假设驱动实验](#m08) | 什么观察能区分几种解释？ | 可复现的实验记录 |
| AI 写完了，人仍接不住 | [09 自我解释](#m09) | 我能解释机制并预测变更后果吗？ | 可核对的机制说明 |
| 方案看起来顺利，风险遗漏多 | [10 失败预演](#m10) | 假设它已经失败，发生了什么？ | 风险、信号与应对 |
| 决策迟迟落地，或改完难恢复 | [11 可逆决策](#m11) | 试错的影响和恢复代价是什么？ | 小步试验与恢复条件 |
| 相同问题反复出现 | [12 事后复盘](#m12) | 哪些条件促成了结果？ | 经过验证的改进行动 |

### 几组容易混用的方法

**苏格拉底式提问与第一性原理**都检查前提。前者通过追问定义、理由和反例改善一个判断；后者从必要条件重新组织解法。前者可以发现“我们对简洁的理解不同”，后者进一步讨论“完成这个任务最低需要哪些信息与操作”。

**JTBD 与双钻**分别聚焦用户要取得的进展、探索与收敛的组织方式。JTBD 可成为双钻发现阶段的一种视角。**权衡矩阵与可逆决策**分别回答“选哪个”与“投入多少审慎、怎样保留退路”。

**失败预演、假设实验与事后复盘**分别处理未来风险、当前解释和已经发生的事件。设想一个故障可以帮助设计测试；证明故障发生过，需要实际记录。

## 3. 十二种方法，怎样进入开发现场

<a id="m01"></a>
### 01 · 苏格拉底式提问：把直觉展开成可检查的判断

苏格拉底式对话通过追问概念、依据及其后果，推动参与者审视自己的判断。[Q1] 本手册把它用于需求澄清与设计评审：先把含糊的词落到行为，再寻找会改变方案的条件。

例如，“列表太乱了”可能指标题与说明层级接近，也可能指任务状态难以辨认。可以问：“请指出一处最影响你找任务的位置”“相同信息量下，哪个页面更易读”“收起说明后，哪些任务会变困难？”这些问题把视觉偏好与功能要求连接起来。

```text
先阅读现有页面和需求，识别含义模糊、会改变实现的词。
挑出最多三个关键问题，分别给出：当前理解、一个具体例子、
一个可能推翻该理解的反例，以及回答将改变哪项设计。
仓库或已给材料能够回答的内容，请自行查证并注明位置。
定义足以支持一个小改动后，汇总为验收条件并进入实现。
```

**收束条件**：双方能用同一组场景判断“符合”与“需要修改”。若追问只是换词重述，就转向截图、原型或操作观察。讨论中的礼貌和允许修正同样重要；提问用于共同理解。

<a id="m02"></a>
### 02 · 待完成任务：从功能名称回到用户想取得的进展

待完成任务（Jobs to Be Done，JTBD）关注人们在具体情境中希望取得的进展。[Q2] “增加批量归档”是解法；“周末整理清单时，迅速移走已完成事项，同时保留找回的把握”更接近要服务的任务。

可以围绕最近一次实际经历询问：什么触发了整理？现在怎样完成？在哪一步费力？为什么继续沿用旧办法？这些回答帮助区分真正的负担与顺手提出的功能。访谈、操作记录与模型构造的场景应分别标记。

```text
把这项功能改写为：当……情境出现时，用户希望……，从而……。
区分触发情境、当前替代做法、主要阻力和成功表现。
引用已有用户反馈；材料不足处标为假设，并给出一个验证问题。
最后提出最小功能范围，以及暂时保留的现有做法。
```

**收束条件**：目标能帮助删除一项无关功能，或确定一条最优先的使用路径。用户画像可以补充背景，具体任务仍需要情境与行为证据。

<a id="m03"></a>
### 03 · 第一性原理：从必要条件重新组织解法

从基本原则和构成要素理解问题，在经典哲学中已有明确讨论。[Q3] 这里采用工程化改写：列清目标、必要条件、经验假设和惯常实现，再尝试在保留必要条件的前提下简化方案。这是一种思考练习，而非某个统一的软件开发标准。

“实时列表必须上复杂消息系统”包含了预先选择的实现。重新展开后，真正的问题也许只是“用户完成操作后应及时看到自己的结果”；跨设备同步、离线编辑和多人协作是否必要，则需要分别确认。必要条件也可以被新证据修订，不能仅凭“显然”确立。

```text
将当前方案拆成目标、必须保持的性质、环境限制、待验证假设和实现偏好。
为每个“必须”注明依据。暂时移除现有技术名称，描述最小可行行为。
再把已有成熟组件放回来，比较复用与新增实现的成本。
输出一个更小的方案，以及最可能使它失效的条件。
```

**收束条件**：得到一个满足已知约束的较小方案，以及需要验证的关键前提。现有组件是可利用的资产，推导的目的在于改善选择与组合。

<a id="m04"></a>
### 04 · 双钻：分别探索问题与解法

Design Council 的双钻（Double Diamond）以发现、定义、发展和交付组织设计过程，体现发散与收敛。[Q4] 用在 AI 协作中，可以先确认值得解决的问题，再比较解决方式，减少从一句愿望直接跳到整套界面的情况。

例如，用户很少使用批量操作，原因可能是入口难发现，也可能是他们需要逐条核对。先观察实际整理过程，再比较常驻工具栏、选择后浮出的操作条和逐条快捷操作。三个方案应在操作方式上有实质差异，而非只有配色变化。

```text
先给出当前问题的两种可能解释，并说明各需要什么观察来区分。
确定本轮工作定义后，给出三种机制不同的低成本方案。
按同一条用户任务比较步骤、发现难度、误操作和恢复方式。
选择一个做小原型，写明继续投入或调整方向的判断条件。
```

**收束条件**：问题定义和候选方案之间有清楚联系，一次原型验证能改变后续决定。四个阶段可往返使用；文案修正等已明确的小任务可以直接实施。

<a id="m05"></a>
### 05 · 权衡矩阵：让取舍可以被解释

NASA 的决策分析方法强调明确决策、评价条件、候选方案和不确定性，并区分必须满足的条件与可权衡的优点。[Q5] 本手册将其缩小为几列比较：先筛选硬约束，再比较真正影响本次决定的差异。

| 方案示意 | 键盘可达：硬条件 | 入口发现性 | 实现成本 | 恢复路径 |
|---|---|---|---|---|
| 常驻批量工具栏 | 待原型验证 | 预计较明显 | 待代码勘察 | 待定义 |
| 选中后出现操作条 | 待原型验证 | 需观察首次使用 | 待代码勘察 | 待定义 |

上表是待填写的分析框架，包含预测与未知。使用分数时，应解释量尺和证据；关键项缺乏依据时，先做小验证比补出小数点更有价值。

```text
比较这些方案：先列必须满足的条件，再选三至五项重要取舍。
每格区分实测、文档依据、推测和未知，说明评分含义。
变动最不确定的一项，检查推荐是否改变。
给出选择理由、接受的代价，以及需要重新讨论的触发条件。
```

**收束条件**：能说明为什么选择它、接受了什么代价、什么新证据会改变选择。将结论写入已有 [ADR 模板](../../templates/ADR.md)，保留真实取舍。

<a id="m06"></a>
### 06 · 系统思维：看见影响路径、延迟与反馈

Meadows 的系统分析强调结构、信息流、反馈与延迟对于系统行为的作用。[Q6] 在软件修改中，可以把问题转成“这项改动会沿哪条关系影响别处”，而非只查看当前函数。

例如，缩短请求超时可能让用户更快看到错误，也可能增加重试；重试增加负载后，又可能使请求更慢。这个反馈链只是待验证解释，需要请求量、耗时、重试次数等观察支持。界面、缓存、持久化与后台任务之间也可以用同样方法追踪。

```text
围绕本次改动，列出直接调用方、状态读取方、持久化位置和异步后续动作。
沿一条用户请求追踪影响，指出延迟、重试和反馈可能出现的位置。
将已读到的依赖与推测的关系分开；为关键关系指定观察点。
优先建议能改善整体结果的小改动，并写明可能转移到别处的成本。
```

**收束条件**：关键影响范围已有检查入口。只画与本次决定有关的关系；全系统巨图往往需要付出更多维护成本。

<a id="m07"></a>
### 07 · 契约与不变量：把“正确”写成行为约定

契约式设计（Design by Contract）用前置条件、后置条件和不变量描述组件间的责任。[Q7] 不变量应注明成立的边界，例如操作完成后、事务提交后或某种稳定状态；中间状态则单独定义。

对“批量归档”可以约定：请求中的事项都属于当前用户且版本有效；成功后，选定事项全部进入归档状态；失败时保持操作前状态；重复提交同一操作返回同一结果。这些是示例产品选择，实际项目也可以采用明确告知用户的部分成功策略。

```text
为这项操作写出前置条件、成功后置条件、失败语义和需要保持的性质。
注明每条约定在哪个边界检查，谁负责保证。
补充重复请求、并发修改、空输入和中途失败时的行为。
为每条重要约定给出一个正例和一个反例，再映射到现有测试入口。
```

**收束条件**：实现者与审查者能按同一组输入、状态和结果判断。约定要接到实际验证；权限检查仍须由可信执行侧承担，界面状态仅表达交互规则。

<a id="m08"></a>
### 08 · 假设驱动实验：让观察区分解释

Zeller 在《The Debugging Book》中把调试组织为提出、检验和修订假设的过程。[Q8] “再让模型修一次”可以改成更具体的实验：“什么观察会支持或推翻这个解释？”

假设一次点击产生两次请求，可能是事件重复绑定，也可能是客户端重试。比较事件触发记录、请求时间与重试标记，再改变单一条件，有助于区分它们。只看错误暂时消失，很难知道改动改变了哪条因果路径。

```text
先列最小复现步骤、预期结果和实际结果。
给出两种有依据的候选解释；针对其中一项写出可反驳的预测。
设计最小实验，记录控制条件、改变的变量、观察点和原始结果。
结论使用“支持、削弱、尚无法区分”，并说明下一步。
定位后保留能在修复前失败、修复后通过的回归用例。
```

**收束条件**：证据已足以选择修复方向，并覆盖原先失败的路径。性能实验同时记录环境、输入规模和重复结果；虚构数字只能作为明确标识的示例。填写 [实验卡](../../templates/EXPERIMENT-CARD.md) 即可保留过程。

<a id="m09"></a>
### 09 · 自我解释：把接手能力交还给开发者

Chi 等人的研究讨论了学习者如何通过自我解释理解例题与相关原理。[Q9] 研究对象是人的学习；这里借用其思路设计代码阅读练习：先自己解释，再对照证据与反馈，检验自己能否预测行为。

例如，看完撤销操作后，尝试说明“它记录了什么”“重新打开应用后如何找回”“事项后来被编辑会发生什么”。模型可据代码指出遗漏，并提供简明机制说明、文件位置和反例；回答的流畅程度需要由代码与运行结果核对。

```text
先让我用自己的话解释这段功能；你对照实际代码检查解释。
指出一处关键遗漏，给出相关文件或测试位置，并问一个变式问题。
最后整理为：输入、状态变化、输出、失败路径和恢复方式。
提供可核验的机制摘要与证据，无需长篇逐步内心推演。
```

**收束条件**：人能独立解释一条主要路径，预测一个条件变化后的结果，并知道到哪里核实。完整掌握所有底层细节可以逐步进行，先覆盖自己要维护的部分。

<a id="m10"></a>
### 10 · 失败预演：在上线前替风险发言

Klein 的失败预演（Premortem）让参与者先设想计划已经失败，再独立提出原因，并据此改善计划。[Q10] 这里把它应用于上线前检查；设想出来的风险仍属于假设。

对“批量归档并支持撤销”，可以设想用户错选了大量事项、成功响应丢失、撤销记录只保存在内存，或撤销覆盖了后来编辑。每项风险都应进一步连接触发条件、早期信号、预防或恢复措施。

```text
假设这项功能发布后，用户无法恢复一次误操作。
先独立列出五个与当前设计有关的可能原因，再逐项对照实现。
为重要风险给出触发条件、可观察信号、最小预防措施和验证方法。
将已发现缺陷与尚待验证的风险分开，选出发布前最值得处理的两项。
```

**收束条件**：风险已改变一项设计、测试或恢复安排。风险数量、戏剧性的失败故事与模型之间的赞同，均应让位于具体证据和行动。

<a id="m11"></a>
### 11 · 可逆决策：按恢复代价决定探索深度

Amazon/AWS 用单向门与双向门区分较难恢复与易于调整的决定。[Q11] 本手册将其转成工程问题：撤回代码、恢复数据和消除外部影响分别需要什么？这些层面的可逆性经常不同。

修改按钮位置通常容易恢复；改变持久化格式、删除记录或对外发送消息，则需要各自的恢复安排。即使某项操作有开关，已经发生的数据变化仍需独立处理。应把“恢复办法已写下”与“恢复演练已完成”分开记录。

```text
把当前决定拆成可独立试验的部分。
分别说明代码、数据、用户操作和外部副作用的恢复方式与代价。
选择影响较小的一步，定义试验范围、停止条件和需要保留的记录。
对难恢复的部分先补证据或安排演练，再推进正式变更。
```

**收束条件**：团队知道何时继续、何时停止，以及恢复由谁执行、用什么验证。重要选择继续使用 [ADR](../../templates/ADR.md)；实际恢复步骤进入任务验收或运维记录。

<a id="m12"></a>
### 12 · 事后复盘：把一次问题变成可复用的改进

Google SRE 的复盘实践强调记录事件、理解促成条件，并形成后续行动。[Q12] 面向个人 AI 开发，也可以用一页记录回答：我们当时知道什么、哪些信号被看见、哪项约定或检查缺失。

“提示词写得差”“模型太笨”难以直接形成修复。更可行动的表达是：“需求只写了撤销，验收未覆盖重启后恢复；实现把记录放在内存中；演示始终在同一会话完成。”每个结论都应与任务记录、代码或测试相联系。

```text
根据实际记录整理影响、时间线、当时可获得的信息和促成条件。
区分事实、合理推断与仍未知的部分，避免以事后知识替代当时情境。
为最重要的原因提出一项具体行动，注明负责人、验证方式和完成条件。
把有效改进放到离错误最近的位置：测试、接口约定、检查脚本或交接模板。
```

**收束条件**：至少一项改进有可检查的完成标准，后续能判断它是否减少同类返工。轻微问题用短记录即可，严重事件再补充完整时间线。

## 5. 三种可直接使用的协作模式

### 目标模糊时：澄清后收束

```text
先读我已给的材料，找出会改变目标、范围或验收的关键未知。
优先使用一种合适的提问方法。每次只问一个最重要的问题，
附两种具体理解与各自影响；事实性问题先自行查证。
当目标与第一条可交付路径清楚时，汇总任务 brief 并停止追加访谈。
```

### 目标清楚时：带着明示假设推进

```text
目标和权限已经明确。先核对仓库事实，列出少量工作假设。
低影响、易恢复的细节沿用现有约定并继续实现；
涉及目标改变、真实数据破坏、费用或权限扩张的事项单独提出。
将未解决但不影响当前切片的问题放入待办，交付时说明证据与剩余边界。
```

### 意见冲突时：用观察替代长篇争论

```text
把两种意见各改写成一条可检验预测。
找出最小、低影响的对照操作，明确观察点与判断条件。
先记录结果，再更新方案；区分实际证据和仍需验证的解释。
证据暂时不足时，优先选择保留调整空间的下一步。
```

提问也有成本。一个实用的停止检查是：**我是否已经知道下一项安全、可验证的小动作？** 若答案明确，就让实现和观察提供新的信息。发布前再用[思考与提问清单](../../checklists/thinking.md)检查关键遗漏。
