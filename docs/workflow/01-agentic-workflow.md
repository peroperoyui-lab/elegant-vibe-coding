# 把一句想法变成可交付的改动

[返回目录](../../README.md) · [快速开始](../../QUICKSTART.md) · [可复制指令](02-prompt-recipes.md)

> **适用范围**：个人项目、已有应用的小步开发、前后端协作。正文是一套可裁剪的方法；项目当前的 `AGENTS.md`、任务 brief、架构决定与交付要求优先。本章场景为虚构教学示例。
>
> **资料核验**：2026-10-21。工具的规则文件加载方式、命令和插件机制会变化；准确区别见[工具与命令](03-tools-and-commands.md)。

## 1. 先选协作方式，再决定流程重量

本手册用下面三个**工作定义**区分任务。它们帮助选择投入程度，名称本身没有统一的行业认证标准。

| 方式 | 人主要负责什么 | 模型主要负责什么 | 适用任务 | 怎样算完成 |
|---|---|---|---|---|
| Vibe coding：自然语言探索 | 描述意图、观察效果、快速调整 | 生成实现、提出变化 | 试验布局、交互草图、一次性小工具 | 预期效果已经看见，原型边界清楚 |
| Agentic coding：代理协作开发 | 决定目标、边界、取舍与验收 | 读仓库、改代码、运行检查、报告证据 | 为已有应用加功能、修故障 | 改动与任务一致，行为有证据，版本可追溯 |
| Spec-driven development：规范驱动开发 | 维护稳定的行为约定 | 根据约定实施并比对结果 | 多模块变更、反复迭代的接口、多人交接 | 规范、实现、验证保持一致 |

三种方式可以出现在同一个项目：先用自然语言探索材料面板，选定交互后写一页任务简报，再让代理完成保存与恢复。**流程的单位是当前改动**。改一处文案，任务描述和实际截图就很充分；改变数据存储格式，则需要额外说明兼容性和恢复办法。

Spec Kit、OpenSpec 等项目把规范与交付组织成可复用流程；这些是可选工具。先理解自己遇到的是需求不清、上下文缺失还是验证不足，再选择对应部分。[W1]、[W2]

## 2. 日常够用的六步循环

| 步骤 | 你交给模型什么 | 让模型交回来什么 | 你主要看什么 |
|---|---|---|---|
| ① 勘察 | 当前仓库、目标、相关界面或错误 | 真实入口、现有机制、相关文件、未知项 | 是否基于当前代码 |
| ② 定义改动 | 谁在什么情境下要完成什么 | 一页 brief：范围、行为、验收 | 能否用具体操作判断完成 |
| ③ 实现一条完整路径 | brief、现有约定、允许修改范围 | 用户入口到数据结果的连通实现 | 是否已经走通一个实际任务 |
| ④ 验证 | 成功与失败场景、运行环境 | 执行命令、观察结果、截图或日志 | 证据是否覆盖本次风险 |
| ⑤ 独立审查 | 原始要求、差异、相关上下文 | 有依据的问题及优先级 | 问题能否复现、影响是否明确 |
| ⑥ 交付与续接 | 提交或分支约定 | 清晰改动说明、版本标识、剩余事项 | 下一次能否顺利接着做 |

这六步可以在一次任务中连续完成。已确定目标、范围和权限时，让模型直接推进；只有会改变产品目标、破坏已有数据、超出授权范围的选择才需要额外决策。日常修改用几行 brief 即可。较长任务再使用仓库的 [TASK-BRIEF](../../templates/TASK-BRIEF.md)、[ACCEPTANCE](../../templates/ACCEPTANCE.md) 和 [HANDOFF](../../templates/HANDOFF.md) 模板。

Claude Code 官方最佳实践强调先探索再实施，并提供可验证结果；本手册进一步把这一原则落实为每一步的交付物，而没有要求每步都增加一次人工审批。[W3]

### 第一步：让模型先认识这份代码

有效的开场是：“先确认当前分支与未提交改动，再读项目约定，定位这项功能的真实入口。”这句话比“你是一位顶级全栈工程师”更能消除实际误差。

勘察的结果最好是一张小表。下表是一份虚构文档管理器的勘察报告，用于比较具体回答与模糊回答：

| 要回答的事 | 有用的答案 | 需要继续核实的答案 |
|---|---|---|
| 从哪进入？ | 点击材料卡片后调用 `openMaterial`，文件路径已列出 | “前端调用后端” |
| 数据从哪来？ | 此视图先读本地索引，再按 materialId 读取正文 | “应该是 SQLite” |
| 目前谁负责？ | 已有 import service 处理文件落盘，可以复用 | “新建一个通用上传系统” |
| 怎么验证？ | 仓库已有导入 fixture 和 smoke 脚本，具体脚本已确认 | “执行 npm test 即可” |

表中的函数、服务、索引和验证脚本均为假设示例。模型应给出目标项目中实际存在的内容。一次勘察只读当前任务需要的入口、数据结构、相关测试与约定；扩大阅读范围应当为了解答具体未知项。

### 第二步：把“感觉”翻译成行为

“做得更专业”仍然可以作为审美意图，但要增加可观察的落点：

> 为文档资料列表建立清晰的三层信息：标题、来源、处理状态。标题最多两行；来源作为次级文字；状态通过文字和图标同时表达。保留现有筛选功能。在正常、空列表、解析中和解析失败四种状态下检查布局。

技术 brief 也一样：

> 导入同一份材料两次时，用户能知道已存在并打开原记录。先检查现有去重依据，再实现与既有模型一致的行为。验收覆盖首次导入、重复导入、同名不同内容、导入失败后的再次尝试。

不要在没有检查代码之前指定“必须增加 Redis”“必须换数据库”之类实现。把目的和验收写清楚，给模型保留实现空间；涉及既定架构时直接指出要复用的机制。

### 第三步：用垂直切片控制规模

**Vertical slice，垂直切片**：一次交付贯穿界面、业务与数据的一条完整路径。以“导入材料”为例，第一片可以只支持一个已约定的文件类型，完成选择文件、导入、显示记录、重启后读取。下一片再增加批量导入或其他格式。

**Horizontal layer，水平分层**：先完成所有页面，再写所有接口，再补持久化。它适合某些明确的架构施工，但个人 AI 开发容易在很长时间后才发现接口理解有偏差。

选择切片时问三句话：

1. 这一片完成后，使用者能独立完成哪件事？
2. 它能用什么输入和输出证明已经连通？
3. 下一片开始时，现有行为是否有稳定依据？

切片大小以“能一次理解和审查”为准，文件数量只是辅助信号。一个小功能改动十个文件可能合理；只改一个文件却引入全局状态、重试和持久化，也可能非常复杂。

### 第四步：把证据等级写清楚

| 证据 | 它能支持的结论 | 下一层还需要什么 |
|---|---|---|
| 静态阅读 | 实现路径与意图基本一致 | 实际运行是否成立 |
| lint / 类型检查 | 特定静态规则或类型约束通过 | 用户行为是否正确 |
| 单元测试 | 被测函数在给定输入下符合预期 | 模块是否正确连接 |
| 集成测试 | 若干真实模块协作符合预期 | 最终界面和真实环境表现 |
| 端到端测试 | 指定用户路径可完成 | 路径之外的状态与平台差异 |
| 人工实测、截图、录屏 | 指定时间与环境中的实际表现 | 重复性、自动回归与更多边界 |

选择与本次改动相关的检查，再运行项目规定的交付 gate。按钮文案修改通常适合截图和点击检查；任务取消涉及状态与持久化，就应覆盖取消前后和恢复后行为。测试的价值来自它能发现哪类回归，数量与运行时长本身很少说明质量。

报告要用准确动词：“运行了”“观察到”“代码中读取到”“尚待 Windows 实机确认”。云端 Linux 的成功结果可以支持其实际覆盖的部分；Windows 文件选择器、托盘、进程退出和安装更新仍要在对应环境验证。

### 第五步：让审查保留独立性

实施者解释“我这样写是因为……”很有帮助，但也会给审查者造成先入为主。给第二个模型的最小材料是：原始任务、变更差异、必须遵守的约定、相关运行证据。让它先独立追踪行为，再参考实施说明。

一个可行动的 finding 应有：**位置 → 触发条件 → 实际后果 → 证据 → 最小修正方向**。把“可以再抽象一下”与“重试会新增第二条记录”分开。前者多为设计建议，后者可能影响数据正确性。模型之间投票赞同，仍然需要对应的可检查依据。

如果审查者提出问题，实施者先复现或用代码证明条件是否成立，再修正。合理的反驳也要留下证据。审查目标是减少实际错误；记录风格偏好时用“建议”，避免把偏好包装成阻塞缺陷。

### 第六步：交付可续接的状态

每次结束保留四件事即可：

- **完成行为**：用户现在能做到什么。
- **验证证据**：哪些命令和场景已执行，结果是什么。
- **版本定位**：工作分支、commit，或者明确的尚未提交状态。
- **下一项任务**：一个具体动作及它需要的输入。

“已全部完成，生产可用”通常信息不足。“导入后列表能显示记录；重启恢复通过；批量拖放尚未覆盖”更能帮助你决定下一步。对于公开指南中的示例，使用虚构数据；项目私有路径、材料正文、密钥和个人日志留在原项目的受控位置。

## 3. 上下文分四层，保持各司其职

**Context engineering，上下文组织**，在日常开发中的实际含义是：让模型在正确时间看到正确材料。它并不要求把整个仓库塞进一条提示词。

| 层次 | 放什么 | 推荐载体 | 多久更新 |
|---|---|---|---|
| 项目长期约定 | 项目用途、当前架构、常用入口、真实验证命令、关键边界 | 项目已使用的 `AGENTS.md` / `CLAUDE.md` / rules | 事实改变时 |
| 功能事实 | 当前接口、状态转换、数据约束、设计规范 | 现有功能文档、契约或设计文件 | 行为改变时 |
| 当前任务 | 目标、允许改动范围、验收、相关证据 | 一页 brief 或任务消息 | 每项任务 |
| 本次现场 | 分支、错误、未提交改动、进度、未解问题 | 会话消息、短交接 | 会话交接时 |

长期文件适合回答“每次来到仓库都必须知道什么”。某次调试日志、完整聊天历史、过期模型排名更适合留在任务记录。把短项目规范作为索引，较长内容通过明确文件链接按需加载。

`AGENTS.md` 是开放的代理说明文件形式；具体读取范围与优先级仍由各工具实现。[W4] Codex 有自己的全局及项目目录发现规则；Claude Code、Cursor 和 Copilot 也有各自的入口。**一个文件名相同，不意味着每个工具的读取行为完全相同。**精确适配见[规则文件对照](03-tools-and-commands.md#rules)。[W5]

### 什么值得写进长期约定

适合写：

> 材料正文由现有 storage service 写入。UI 通过既有服务接口请求变更。变更提交前运行仓库定义的相关测试和交付 gate；具体命令见开发说明。

适合放在当前任务：

> 这次只完善材料列表的空状态和加载状态；截图基于 1366×768 窗口。已有筛选交互按当前代码保留。

适合归档为历史：

> 如果项目发生过运行时迁移，可将旧说明移入历史记录，并标明适用版本。

长期维护项目时，应把历史说明与当前依据区分开。架构说明可附更新日期或适用版本，任务 brief 则指向本次适用的文档。

### 长期规则的精简方法

每条规则问：它解决过哪个真实问题？现在仍成立吗？是通用常识还是项目特有事实？能否由脚本或类型系统自动检查？

“写优雅、专业、先进的代码”几乎没有可操作信息。“追加记录时用已有 transaction helper；失败必须返回可重试状态”有明确落点。重复的口号可以删除，自动检查能承担的约束交给工具，关键产品事实保留在短文档中。OpenAI 近期官方建议也强调，随着模型和工作流变化，应重新检查积累的规则与提示词是否仍然必要。[W6]

## 4. 任务指令的六个槽位

需要复杂任务时，按这个顺序写。小任务可以压缩成一个自然段。

| 槽位 | 你写什么 | 示例 |
|---|---|---|
| 目标 | 用户可感知的结果 | 恢复上次打开的工作空间 |
| 背景 | 现状和触发原因 | 重启后目前总回到项目列表 |
| 范围 | 本次允许修改的部分 | 启动恢复流程和对应测试 |
| 约束 | 当前项目事实与必要边界 | 复用现有持久化；项目不存在时回到选择页 |
| 验收 | 成功、失败、边界场景 | 有记录、记录指向已删除项目、首次启动 |
| 交付 | 需要的成果与证据 | 改动、相关验证、未验证环境说明 |

一个表达清楚的目标，经常比一页角色设定更有效。模板的作用是提醒你补全关键输入；填完后可以删掉空栏目，保持自然语言的可读性。

## 5. 分工：按任务边界组织多个模型

| 角色 | 输入 | 输出 | 最适合的工作 |
|---|---|---|---|
| 勘察者 | 问题和只读权限 | 事实地图、真实入口 | 查旧代码、找复用机制 |
| 实施者 | brief 和相关上下文 | 小而连通的改动 | 写代码、修复、验证 |
| 审查者 | 要求、diff、证据 | 有依据的缺陷与疑问 | 挑边界问题、核对回归 |
| 视觉审阅者 | 设计目标与实际截图 | 按层级排序的修改意见 | 排版、密度、状态一致性 |
| 负责人 | 所有交付摘要 | 取舍、集成与下一步 | 保持产品方向和范围 |

同一模型可以先后承担不同角色；跨模型独立审查也有价值。模型选择取决于具体任务的表现、工具能力与预算，固定的“某模型永远写前端、某模型永远审后端”会很快过期。

能并行的是互相独立的调查或有明确文件归属的改动。共享核心类型、同一数据库迁移、同一界面文件，适合先确定接口再顺序整合。使用 Git worktree 能给每条分支独立工作目录，但数据库文件、服务端口、外部账户和临时目录仍需单独安排。[W7]

给子任务至少说明：“你拥有哪些文件、依赖谁的接口、何时算完成、怎样交还证据”。若前端与后端并行，可以先约定一个最小响应样例和错误结构，让双方围绕同一个行为实现；样例是否符合现有项目契约仍应先核实。

## 6. 调试失控时，先恢复问题定义

| 现场症状 | 常见原因假设 | 下一步有效动作 |
|---|---|---|
| 同一错误反复修改 | 每次只处理表面报错 | 固定复现输入，沿调用链找到第一次偏离预期的位置 |
| 修完 A 又坏 B | 修改范围扩张、共享假设未显式化 | 检查 diff，提取共同约束，增加针对回归的用例 |
| 模型总在错误文件改动 | 入口识别错、旧背景污染 | 重新定位运行入口和真实版本，更新当前 brief |
| 测试全过、功能仍异常 | 测试只验证 mock 或局部逻辑 | 走一遍真实用户路径，核对接线和持久化 |
| 越改文件越多 | 把局部问题升级成架构重做 | 暂停范围扩张，要求解释每个新增改动与目标的关系 |
| 上下文塞满、回答漂移 | 累积了大量历史尝试 | 写短交接，保留复现、已证伪假设和下一项实验 |

**调试记录应保留被证伪的假设。**“怀疑是缓存；清空缓存后仍复现”比“尝试修复多次”更能节省下一轮工作。每次实验只改变少量条件，运行相同复现路径，记录结果，然后更新判断。

在可恢复的开发环境里，合理假设可以继续推进。会改变用户数据或已发布接口的假设，先把影响和可验证选项说明清楚。以真实阻碍决定是否停下来，减少无意义的反复确认。

## 7. 对个人长期项目的最小配置

先拥有下面五样，已经足以组织大量工作：

1. 一个简短、与当前代码一致的项目说明入口。
2. 每次一个清楚的任务 brief。
3. 一套真实可运行的相关验证命令。
4. 一次针对行为的独立 review。
5. 能定位版本和继续工作的交付记录。

遇到反复出现的问题，再增加一个专用模板或自动检查。需要跨多个功能持续维护规范时，再考虑 OpenSpec 或 Spec Kit；需要团队角色编排时，再研究 BMAD；希望复用调试、计划与审查技能时，再评估 Superpowers。采用理由应当能具体到“它解决了我们哪项重复工作”。

采用本手册时，可以先改善任务说明、设计反馈和验证记录，再按实际需要增加模板或工具。
