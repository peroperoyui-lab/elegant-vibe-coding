# 设计评审：怎样给反馈，怎样判断模型真的改好了

[返回目录](../../README.md) · [快速开始](../../QUICKSTART.md)

> 评审方法、时间盒与问题等级为本手册建议，可按团队约定调整。截图适合判断可见结构；键盘、数据正确性、性能和状态恢复需要对应的运行证据。

高质量反馈有四个部分：**在哪个位置、观察到什么、影响哪个任务、希望变成什么**。例如：“材料列表的来源标签和标题使用同样深色，扫描时较难定位标题；请将来源降到辅助文字层级，同时保留可读对比。”这比“再高级一点”更容易稳定复现。

## 1. 先决定这次评审的对象

| 评审对象 | 核心问题 | 需要的证据 | 本轮适合的改动 |
| --- | --- | --- | --- |
| 艺术方向 / Art direction | 风格是否服务于产品定位与任务？ | 三种方向板，使用同样内容比较 | 字体、配色、表面、图像方向 |
| 信息设计 / Information design | 用户能否快速找到当前对象和下一步？ | 真实内容与任务路径 | 排序、分组、层级、导航 |
| 视觉精修 / Visual polish | 规则是否一致，细节是否稳定？ | 同环境前后截图 | 对齐、间距、字重、边框、图标 |
| 交互审查 / Interaction review | 状态变化和错误恢复是否完整？ | 实际操作、录屏、状态样本 | 焦点、状态、反馈、取消与重试 |
| 实现审查 / Implementation review | 代码是否复用系统并保持正确性？ | diff、DOM、组件契约、运行结果 | token 复用、状态管理、语义修复 |
| 性能审查 / Performance review | 真实任务是否及时、稳定？ | 测量条件、轨迹、采样数据 | 渲染、请求、列表策略与资源加载 |

一次先解决最影响任务的层次。信息分类混乱时，微调阴影的收益有限；任务已经顺畅时，统一图标和文字节奏会明显改善完成度。

## 2. 评审顺序：结构 → 状态 → 视觉 → 实现

### 第一步：用真实任务读页面

假设读者刚打开项目，要找到一份材料、确认来源、运行一次分析，然后回看结果。请指出每一步在哪里发生、是否需要猜测、关键信息是否被隐藏。关键按钮的名字应描述实际动作，演示数据和真实数据要能辨别。

### 第二步：把默认截图展开成状态集合

至少挑选与本次改动相关的空白、加载、长内容、错误、选中、焦点和窄窗口情境。长任务还应检查取消中、部分完成与连接中断。状态数量按风险决定，重点覆盖真实分支。

### 第三步：检查视觉秩序

先看主次与空间，再看颜色、图标和投影。观察标题和主要操作是否抢占同一注意力，边栏是否压过内容，表格是否适合连续比较。用户眼睛要去的地方，应当与任务步骤一致。

### 第四步：确认实现遵守规则

查看视觉值是否来自现行 tokens，是否为一个局部问题新增了重复组件，是否把纯展示改动混入了业务逻辑。截图里看起来合理的禁用按钮，可能没有解释理由；看起来一致的两个条目，也可能有完全不同的键盘行为。

## 3. 给模型的截图反馈语法

推荐句式：

> **位置** + **可见现象** + **任务影响** + **修改方向** + **验收标准**。

| 类型 | 可直接复制的反馈 |
| --- | --- |
| 层级 | “左侧材料列表中，标题、来源、时间使用近似字重，扫描负担偏高。请建立主标题—来源—时间三级关系，用真实长标题验证。” |
| 位置 | “顶部标题与正文起点偏离。请统一共享左边界，并检查搜索框、列表和空状态是否沿用。” |
| 间距 | “同组字段和不同字段组的间距接近。请让组内更紧、组间更松，按照现有 spacing tokens 实现。” |
| 密度 | “每个任务都套入大卡片，首屏只能看到少量条目。请试列表结构，保留清楚状态与主要动作。” |
| 颜色 | “过多区域同时使用品牌色。请把最强强调留给当前动作与选中对象，再测辅助文字可读性。” |
| 图标 | “同一工具栏混用填充和细线图标。请统一图标家族、光学尺寸和标签策略。” |
| 状态 | “失败后只出现短暂 toast。请在相关任务旁保留错误原因与重试入口，并验证重进页面后的状态。” |
| 反馈 | “点击开始后界面保持静止，用户容易重复提交。请立刻显示已接收状态，并使用服务结果更新后续阶段。” |
| 阅读 | “正文在宽屏下横跨整个工作区。请设置阅读宽度，并让来源详情使用剩余空间。” |
| 可访问性 | “图标按钮缺少可访问名称。请逐个按动作命名，随后用键盘和可访问性树核对。” |
| 长内容 | “文件名在较窄窗口中挤占状态列。请为标题提供换行或完整查看方式，并保持状态可识别。” |
| 动效 | “每次切换材料时所有区块都移动。请把动效集中到必要的状态变化，并验证减少动态效果设置。” |

反馈最好一次聚焦一到三类高影响问题，完成后用相同数据再看效果。对整个项目提出统一风格时，先改一个代表页面，再逐步推广。

## 4. 比较艺术方向：把审美实验控制在同一条件下

让模型提供三种视觉方向时，保持**相同功能、相同文案、相同数据、相同视口**。如果 A 用漂亮的短文，B 填满长文件名，就难以知道差异来自风格还是数据。

下面是一组通用研究工具的教学比较方案。实际项目已有艺术基线时，可以将它用作局部实验，而不自动替换现行品牌。

| 维度 | A 编辑式阅读 | B 紧凑研究工具 | C 温和知识空间 |
| --- | --- | --- | --- |
| 主要目标 | 深度阅读与写作 | 高频切换、筛选、核查 | 个人积累与持续阅读 |
| 排版 | 较强标题与舒展正文 | 固定、稳定的控件与列表层级 | 柔和中性色与清楚正文 |
| 结构 | 阅读面优先，边注辅助 | 主从视图，快捷操作明确 | 内容分组与返回路径突出 |
| 颜色 | 文字与内容承担表达，少量品牌强调 | 状态和选中表达准确 | 暖中性表面，少量强调 |
| 最需观察 | 标题占位是否影响日常效率 | 密度是否让长文阅读疲劳 | 层级是否因过度柔和而变弱 |
| 验证任务 | 连续阅读三段并添加注释 | 从多项材料中找到目标并执行 | 重开项目后找回上次阅读位置 |

用任务回答比较问题：“哪个方案让证据与结论更容易对照？”“哪个方案的失败状态更容易恢复？”再问“哪个更符合品牌性格？”审美偏好可以保留，但它与任务证据分别记录。

```text
请在同一页面内容上提供3个艺术方向：编辑式阅读、紧凑研究工具、温和知识空间。
三版保持相同功能、文案、演示数据和视口，只改变设计语言。
每版说明字体层级、空间、色彩、表面和交互重点，并给一张完整状态截图。
另外展示长标题、错误与键盘焦点，让我比较日常使用效果。
最后给你的推荐和具体理由，明确推荐依据与仍待用户验证的假设。
```

## 5. 常见“AI 模板感”与具体修正

| 现象 | 可能的设计原因 | 更有效的修正 |
| --- | --- | --- |
| 所有内容都装进圆角卡片 | 组件先于信息分类 | 列表负责扫描、表格负责比较、阅读面负责长文、卡片负责独立对象 |
| 标题很大，内容很少 | 沿用营销落地页比例 | 工作区标题让位于真实任务；介绍性页面可保留表达型标题 |
| 每块都有渐变、光晕与投影 | 层高和强调缺少分工 | 常驻表面安静，临时浮层突出；品牌装饰集中在有意义位置 |
| 一屏多个强色 CTA | 主要动作未定义 | 每个当前任务明确主动作，次要与危险动作另设层级 |
| 文案都是“解锁潜能” | 缺少用户任务与真实内容 | 写具体对象、动作、结果与限制，如“从材料中提取候选证据” |
| 空状态只有插图 | 缺少原因和下一步 | 首次使用、筛选为空、读取失败分别写文案和动作 |
| 漂亮的进度条缓慢走满 | 进度缺乏真实信号 | 有总量用真实数量；阶段未知时显示阶段或等待说明 |
| 只有鼠标 hover 才出现操作 | 默认图为了干净隐藏了功能 | 关键入口稳定可见；次要操作也能通过聚焦或清楚菜单抵达 |
| 所有字号都偏小 | 把密度理解成缩小文字 | 先压缩重复容器与无效空间，再调整密度档位 |
| 圆角、边框、图标各不相同 | 多轮局部修改失去约束 | 列出现有 token 与组件，整合重复实现，保留有意义差异 |

这些判断针对功能与形式的关系。某种视觉元素可以是正确选择；评审的重点是它在当前页面承担什么职责。

## 6. 前端快速 review：十五分钟版本

| 时间盒 | 看哪里 | 要回答的问题 | 建议产物 |
| --- | --- | --- | --- |
| 0–3 分钟 | 需求、diff、页面入口 | 改动为谁解决什么问题？范围是否清楚？ | 一句变化摘要 |
| 3–6 分钟 | 主任务与状态分支 | 成功、失败、重复点击、取消、重试是否连贯？ | 复现步骤与实际结果 |
| 6–9 分钟 | 键盘、标签、焦点、缩放 | 核心任务是否可完成？状态信息可感知吗？ | 已验证项目与待验证项目 |
| 9–12 分钟 | 长内容、窄窗口、主题 | 是否溢出、遮挡、层级失衡？ | 一组有环境说明的截图 |
| 12–15 分钟 | 组件与状态实现 | 是否重复造组件、误用语义、丢失输入或来源？ | 按影响排序的问题清单 |

时间到后记录剩余风险；需要进一步验证的具体问题再单独展开。把已证实的问题与建议优化分开，能避免“必须重构”“最好优化”混在同一优先级里。

### 问题等级建议

| 等级 | 判断依据 | 例子 |
| --- | --- | --- |
| 阻断 | 关键任务无法完成、内容丢失、敏感内容意外暴露 | 点击取消仍显示成功并覆盖已保存结果 |
| 高 | 常见流程严重受影响，恢复困难或状态误导 | 错误后丢失输入；模态框无法用键盘关闭 |
| 中 | 功能可完成，但特定条件下明显影响效率或可读性 | 长文件名挡住状态；暗色主题辅助文字难读 |
| 低 | 局部一致性与精修问题 | 同一工具栏图标光学尺寸略不一致 |

等级以影响、发生条件和可恢复性判断，团队可以使用自己的 P0–P3 或其他命名。

### 好的审查发现长什么样

```text
等级：高
位置：材料导入对话框 / 提交错误处理
触发：填写三个材料路径 → 模拟服务超时 → 再次打开对话框
实际：三个输入全部清空，页面只保留“失败”短提示
影响：用户需要重新查找路径，无法从上次失败点继续
证据：录屏时间点、实际组件路径、相关错误分支
建议：保留草稿与逐项状态；在对话框内显示可重试原因
最小回归：超时后输入仍在；重试只处理尚未完成项；关闭与重开行为符合规格
```

组件路径与行号必须来自实际检查。审查者无法运行时，应说明这是代码推断，并提供最短验证步骤。

## 7. 截图、自动化与性能证据怎样使用

### 截图应该可比

固定视口、设备缩放、浏览器版本、字体、主题、测试数据和页面状态，再比较前后。等待字体与相关内容稳定，减少时间戳、随机内容和持续动画造成的噪声。Playwright 提供截图比较能力，官方也提醒操作系统、浏览器及环境差异会影响渲染；基线与回归应尽量在同环境运行。[Playwright：Visual comparisons](https://playwright.dev/docs/test-snapshots)

更新截图基线应当意味着“这个视觉变化已被理解并接受”。先看差异解释，再接受新基线。对小型静态样式改动，人工同屏比较可能已经足够；对高频更新的核心页面，自动截图回归更值得维护。

### 自动无障碍扫描覆盖部分问题

可以在已有测试环境里使用相应扫描工具，检查缺失标签、部分对比度、错误属性等。先把菜单、对话框和错误状态实际打开，再扫描。工具结果与人工键盘、屏幕阅读器和实际用户流程共同使用；Playwright 与 WAI 都明确说明自动检查有覆盖边界。[Playwright：Accessibility testing](https://playwright.dev/docs/accessibility-testing) · [WAI：Evaluation tools](https://www.w3.org/WAI/test-evaluate/tools/)

### 性能指标对应什么

网页的 Core Web Vitals 当前包括 LCP、INP、CLS；官方良好阈值分别是 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1，面向真实用户访问分布通常按第 75 百分位、区分移动与桌面考察。[web.dev：Web Vitals](https://web.dev/articles/vitals)

桌面资料管理工具可以借鉴“加载、交互、视觉稳定”三种关注点，再补充自身任务指标，例如切换材料后多久可阅读、输入时是否卡顿、大列表滚动是否持续顺畅、流式输出是否阻塞界面。一次本地测量是一次观察；报告时写清数据规模、硬件、运行环境、冷/热启动与次数。模型推理耗时和界面反馈耗时分别测量，才能知道应该改善哪里。

## 8. 四种可直接使用的指令

### A. 只做设计诊断

```text
请根据截图和实际页面做设计诊断，先读取现有设计约定。
按信息层级、布局、排版、色彩、状态和可访问性检查。
每条写清位置、现象、任务影响、建议和验证方式。
最多先给5个最值得处理的问题，按影响排序。
对截图能确认的事实、代码推断和仍需实测的内容分别标注。
```

### B. 进行一次有边界的视觉精修

```text
本轮精修材料列表与阅读面。
目标：提升长标题扫描、正文阅读和状态识别。
先核对现有tokens与组件，复用既有艺术方向。
调整层级、间距、对齐与图标；涉及信息结构或交互行为的变化单独说明。
交付同数据同视口的前后对照、修改理由、已验证状态与剩余风险。
```

### C. 找出前端回归

```text
请以独立reviewer身份审查这次前端diff。
先了解实际需求，再沿受影响的用户路径验证。
重点找状态错误、输入丢失、焦点问题、溢出、重复请求和危险内容渲染。
每个发现给具体代码位置、复现条件、影响与最小修复。
区分已确认bug、待验证风险和可选优化；如无实质问题，也说明检查范围。
```

### D. 为实现补一页专业设计说明

```text
为本次界面实现撰写设计说明。
用五部分组织：使用任务、结构安排、视觉规则、交互状态、验证证据。
每个重要设计决定连接到具体用户任务，并列出关键取舍。
引用实际tokens、组件和状态；数值建议与标准要求分别注明。
文案通俗准确，让非设计专业的项目负责人也能判断结果。
```
